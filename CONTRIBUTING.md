# Как вносить изменения

Перед правкой прочитай [`DOCUMENTATION_POLICY.md`](DOCUMENTATION_POLICY.md) и
определи назначение документа. Общая инструкция, состояние ASUS ExpertBook
B5402 и история конкретного события должны оставаться разными слоями.

## 1. Выбери класс документа

- `guide` — повторяемая процедура;
- `reference` — справочный материал или инвентаризация;
- `troubleshooting` — решение воспроизводимого симптома;
- `incident` — датированное расследование одного события;
- `system` — фактическое состояние эталонной машины;
- `policy` — правила репозитория.

Если руководство содержит локальные пути, версии, результаты команд или
утверждения о текущей машине, временно укажи `scope: mixed` и запланируй
разделение. Не маскируй смешанный документ значением `scope: general`.

## 2. Добавь метаинформацию

Пользовательские документы создаются в `src/content/docs/`. Для нового
документа используй минимальный шаблон:

```yaml
---
title: Название документа
kind: guide
scope: general
status: draft
last_verified: null
verified_on: []
---
```

`title` — обязательное поле Starlight: это название документа и отображаемый
заголовок страницы. H1 в теле Starlight-документа не используется; обычный H1
остаётся для repository-level Markdown вне `src/content/docs/`.

Для проверки на эталонном ноутбуке:

```yaml
last_verified: 2026-09-09
verified_on: [asus-b5402]
```

Не меняй `last_verified`, если проверялась только грамматика, Markdown-разметка
или ссылка. Для непроверенного технического состояния оставляй `null`.

## 3. Пиши в стиле проекта

- Основной язык — русский; названия пакетов, параметров и upstream-проектов
  сохраняются на английском.
- Пакеты Gentoo записываются как `category/package`.
- Перед конфигурацией указывается путь: `Файл: /path/to/config`.
- Команды с повышенными привилегиями используют `doas`, если исключение не
  объяснено в тексте.
- Fenced code block должен иметь подходящий язык: `bash`, `conf`, `ini`,
  `makefile`, `toml`, `kdl`, `nft` или другой точный формат.
- Предупреждения должны называть конкретный риск и способ отката.
- Для персональных путей используется `$HOME`, `~` или понятный placeholder.

## 4. Проверь техническую границу

Перед добавлением системных значений ответь на четыре вопроса:

1. Это общая рекомендация, пример или наблюдение на `asus-b5402`?
2. Когда и чем утверждение было проверено?
3. Может ли значение измениться после обновления пакета или системы?
4. Не раскрывает ли пример секрет, устойчивый идентификатор или лишнюю
   информацию о локальной топологии?

Если ответ неизвестен, обозначь ограничение прямо и не заполняй
`last_verified` предположительной датой.

## 5. Проверь изменение

Минимальная локальная проверка:

```bash
git status --short --branch
git diff --check
```

Если `markdownlint-cli2` установлен, запусти его только для изменённых
Markdown-файлов. Дополнительно проверь:

- внутренние ссылки и якоря;
- парность fenced code blocks;
- существование упомянутых файлов;
- соответствие frontmatter принятому словарю;
- отсутствие секретов и персональных идентификаторов;
- наличие verification и rollback в рискованных процедурах.

Команды из самих runbook не являются тестами. Не запускай `emerge`, `doas`,
`systemctl`, `nft`, `mount`, `dracut`, `sbctl` или
`systemd-cryptenroll` только для проверки документа.

## 6. Подготовь изменение к проверке

- Не смешивай перенос файлов с массовой редактурой содержания.
- После перемещения обнови все входящие ссылки и `README.md`.
- При существенном изменении русского документа проверь наличие
  соответствующего `en/`-перевода и синхронизируй его либо явно оставь
  fallback (`DOCUMENTATION_POLICY.md` §10).
- Не удаляй устаревший документ, пока полезная уникальная информация не
  перенесена или не признана ненужной.
- Сохраняй небольшие тематические изменения.
- Используй префиксы сообщений `add:`, `update:`, `change:` или `fix:`.

В описании изменения укажи, что проверено локально, что подтверждено на живой
системе и что осталось непроверенным.
