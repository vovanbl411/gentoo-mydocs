Разделение Btrfs на субволюмы позволяет управлять областями файловой системы
отдельно: включать нужные данные в снимки, исключать из них логи и кэши и
применять там, где это возможно, отдельные VFS options или атрибуты для
специальных workload. Большинство Btrfs-specific mount options действует на
всю файловую систему, а не на отдельный субволюм.

В этом руководстве используется flat layout: субволюмы создаются на одном
уровне и монтируются в нужные каталоги. В результате корень, домашние данные,
снимки и изменяемые служебные каталоги не зависят от вложенной иерархии
субволюмов.

Приведённая ниже схема — пример, а не обязательная конфигурация для любой
системы. Выбирай субволюмы по тому, какие данные должны попадать в снимки и
какие каталоги требуют отдельных VFS options или атрибутов. Фактический layout
ASUS B5402 записан в
[системном разделе](../../systems/asus-b5402/filesystem/layout-and-snapshots/).

## Когда применять эту схему

Подход подходит для корневой файловой системы Btrfs, если нужно раздельно
управлять снимками, постоянными данными, кэшами и временными файлами. До
создания layout определи:

- что должно входить в снимок корня;
- какие данные нужно хранить в отдельном субволюме;
- какие Btrfs-specific options будут действовать на всю файловую систему;
- какие точки монтирования будут использовать tmpfs или отдельные VFS options,
  а какие workload требуют атрибутов файлов или каталогов;
- сколько памяти можно отдать под сборку Portage.

Ожидаемый результат — понятный набор независимо монтируемых субволюмов, где
снимки не захватывают ненужные логи, кэши и временные данные.

## Общий design

Flat layout отделяет логическую структуру субволюмов от каталогов, в которые
они монтируются. Само имя `@`, `@home` или `@snapshots` не задаёт точку
монтирования: соответствие определяется конфигурацией монтирования системы.

Выделяй отдельный субволюм только там, где нужна отдельная граница снимков или
отдельная точка монтирования. Субволюм сам по себе не создаёт независимый набор
Btrfs-specific mount options: большинство таких параметров применяется ко всей
файловой системе и обычно определяется её первым mount. Большое число
субволюмов само по себе не является целью.

## Пример layout

Один из возможных вариантов:

| Субволюм | Точка монтирования | Назначение |
|----------|--------------------|------------|
| `@` | `/` | корень системы |
| `@home` | `/home` | пользовательские данные |
| `@snapshots` | `/.snapshots` | снимки Snapper |
| `@var_log` | `/var/log` | логи вне снимков корня |
| `@var_cache` | `/var/cache` | системный кэш |
| `@distfiles` | `/var/cache/distfiles` | исходные коды пакетов |
| `@ccache` | `/var/tmp/ccache` | кэш компилятора C/C++ |
| `@portage_tree` | `/var/db/repos/gentoo` | дерево Gentoo |
| `@docker` | `/var/lib/docker` | данные контейнеров Docker |
| `@libvirt` | `/var/lib/libvirt` | образы виртуальных машин KVM/QEMU |
| `@portage_tmp` | `/var/tmp/portage-disk` | временные файлы тяжёлых сборок |

Не копируй этот список целиком без необходимости. Например, отдельные
субволюмы Docker, libvirt или ccache нужны только при использовании
соответствующей нагрузки.

## Mount options

Для NVMe в `/etc/fstab` можно использовать следующие параметры:

- `ssd` — оптимизация под твердотельные накопители;
- `compress=zstd:3` — прозрачное сжатие с балансом скорости и экономии места;
- `discard=async` — фоновая очистка неиспользуемых блоков (TRIM).

Это Btrfs-specific options. Как и `nodatacow`, они относятся к файловой системе
целиком и обычно задаются её первым mount; повторное указание разных значений
для субволюмов не создаёт независимые режимы работы.

Обычные VFS options могут применяться к отдельной точке монтирования, если это
поддерживает конкретная опция. Например:

- `noatime` — отключение записи времени последнего доступа для выбранного
  mount.

Для специальных workload используй per-file или per-directory attributes и
properties, когда они применимы. Например, `chattr +C` задаёт NOCOW для вновь
создаваемых данных через атрибут каталога, а не отдельный режим субволюма.

## tmpfs для Portage

Рабочую директорию Portage можно вынести в оперативную память, чтобы уменьшить
запись временных данных на SSD и ускорить компиляцию пакетов:

- `/var/tmp/portage` — пример точки монтирования tmpfs;
- размер выбирается по объёму RAM и требованиям сборки.

Перед таким изменением учитывай пиковое потребление памяти при сборке крупных
пакетов. Дисковый `/var/tmp/portage-disk` из примера layout остаётся отдельным
вариантом для тяжёлых сборок.

## CoW и NOCOW

Btrfs по умолчанию использует Copy-on-Write (CoW). Это полезно для снимков и
защиты от повреждений, но файлы, которые постоянно перезаписываются мелкими
блоками, могут сильно фрагментироваться и терять производительность, особенно
по IOPS. К таким данным в этом примере относятся:

1. образы виртуальных машин в `/var/lib/libvirt/images`;
2. образы и тома баз данных Docker;
3. временные файлы компиляции в `/var/tmp/portage-disk`;
4. постоянно перезаписываемые объекты ccache в `/var/tmp/ccache`.

Это список нагрузок из примера, а не требование отключать CoW на каждом
одноимённом субволюме.

### Применение `chattr +C`

> **Важное правило Btrfs**: атрибут `C` на каталоге наследуют вновь создаваемые
> в нём файлы. Существующие файлы автоматически не становятся NOCOW, поэтому
> атрибут нужно задавать до создания новых файлов или копирования существующих
> данных в подготовленный каталог.

Для пустых каталогов:

```bash
# Для виртуальных машин
doas chattr +C /var/lib/libvirt/images

# Для временной директории Portage на диске
doas chattr +C /var/tmp/portage-disk

# Для ccache
doas chattr +C /var/tmp/ccache

# Для существующего пустого тома БД в Docker, если он есть
doas chattr +C /var/lib/docker/volumes/my_db_volume/_data
```

> **Примечание**: данные NOCOW не используют data checksums и compression.
> Атрибут `C` на каталоге задаёт это поведение для новых файлов, которые его
> наследуют; существующие файлы он автоматически не изменяет.

### Перенос существующих файлов

Если в `/var/lib/libvirt/images` уже лежат образы, сначала останови процессы,
которые могут их изменять, и убедись, что есть актуальная резервная копия.
Создай новый каталог с атрибутом `+C` и скопируй данные без reflink:

```bash
doas mkdir /var/lib/libvirt/images_new
doas chattr +C /var/lib/libvirt/images_new
doas cp -a --reflink=never /var/lib/libvirt/images/* /var/lib/libvirt/images_new/
```

Проверь полноту копии до удаления исходного каталога. Команда ниже
безвозвратно удаляет исходные образы; выполняй её только после проверки и при
остановленных виртуальных машинах:

```bash
doas rm -rf /var/lib/libvirt/images
doas mv /var/lib/libvirt/images_new /var/lib/libvirt/images
```

Если проверка копии не прошла, не удаляй исходный каталог: исправь перенос или
удали только новый `images_new` и повтори процедуру.

## Maintenance

Для контроля состояния Btrfs используй scrub; в этом примере проверка
целостности запускается раз в месяц. Balance перераспределяет данные и
актуален, если диск заполнен более чем на 80%; это не часть каждой обычной
проверки.

```bash
# Просмотр статистики ошибок устройства
doas btrfs device stats /

# Запуск фоновой проверки целостности
doas btrfs scrub start /

# Проверка статуса запущенного scrub
doas btrfs scrub status
```

Запуск scrub может быть долгой операцией на живой файловой системе. Планируй
его с учётом текущей нагрузки и отслеживай состояние отдельной командой.

## Verification

После настройки проверь:

- точки монтирования и соответствующие им субволюмы;
- ожидаемые mount options;
- что tmpfs смонтирован в выбранную рабочую директорию Portage;
- атрибут `+C` на каталогах, где он был задан до записи данных;
- статистику ошибок и состояние последнего scrub.
