Snapper создаёт снимки Btrfs и управляет ими: позволяет сравнивать снимки,
откатывать изменения и восстанавливать отдельные файлы. Он не заменяет
отдельную резервную копию данных и не создаёт снимки вокруг `emerge` без
дополнительной интеграции с Portage.

В этом руководстве используется конфигурация `root` для корневого субволюма
`@`. Автоматические timeline-, cleanup- и boot-операции выполняют systemd
timers. Portage pre/post hook описан отдельно как необязательный вариант; на
ASUS B5402 он сейчас не активен.

Ожидаемый результат — доступная пользователю история снимков, автоматическое
создание и удаление по заданной политике и понятный способ проверить таймеры и
занимаемое место. Подтверждённое состояние ASUS B5402 и дата его проверки
записаны в [системном разделе](../systems/asus-b5402/filesystem/layout-and-snapshots.md).

## Prerequisites

Перед настройкой нужны:

- корневая файловая система Btrfs;
- отдельное место для снимков, например субволюм `@snapshots`, смонтированный
  в `/.snapshots`;
- конфигурация Snapper `root` для точки монтирования `/`;
- выбранная политика хранения с учётом свободного места.

Снимок Btrfs остаётся на той же файловой системе. Для независимого
восстановления после потери накопителя нужна отдельная резервная копия.

## Конфигурация и права

Файл: `/etc/snapper/configs/root`

Чтобы пользователи группы `wheel` могли управлять снимками без root, задай:

```conf
ALLOW_GROUPS="wheel"
SYNC_ACL="yes"
```

После изменения конфигурации примени права:

```bash
doas snapper -c root setup-acl
```

## Автоматические снимки и systemd timers

Для автоматического управления используются следующие таймеры:

- `snapper-timeline.timer` создаёт ежечасные снимки;
- `snapper-cleanup.timer` раз в час запускает очистку старых снимков по
  лимитам из конфигурации;
- `snapper-boot.timer` опционально создаёт снимок при каждой загрузке.

Проверь активность и следующее время запуска:

```bash
systemctl status "snapper-*.timer"
systemctl list-timers "snapper-*"
```

Принудительный запуск cleanup нужен для обслуживания или проверки политики, а
не для обычного создания снимка:

```bash
doas systemctl start snapper-cleanup.service
```

## Интеграция с Portage

Pre/post-снимки вокруг `emerge` не являются обязательной функцией базовой
настройки Snapper. Для них нужен отдельный hook, например в
`/etc/portage/bashrc`: перед операцией он создаёт снимок Pre, после неё —
связанный снимок Post.

На эталонной ASUS B5402 Portage pre/post hook сейчас не используется.
Актуальное подтверждённое состояние находится в
[системном разделе](../systems/asus-b5402/filesystem/layout-and-snapshots.md).

Если снимки вокруг `emerge` снова понадобятся, hook нужно вернуть как отдельное
осознанное изменение. Это не требуется для timeline- или boot-снимков.

## Политика очистки

Лимиты не дают снимкам бесконтрольно занимать место. Подбирай их под объём
файловой системы и требуемую глубину истории.

Ниже приведены значения ASUS B5402 как пример, а не универсальная норма:

- timeline хранит 5 последних часов и 7 последних дней; недельный лимит — 1,
  месячный — 0;
- `NUMBER_LIMIT="10"` ограничивает numbered-снимки, которые обрабатывает
  cleanup `number`, независимо от способа их создания;
- `SPACE_LIMIT="0.8"` задаёт максимальную долю пространства файловой системы,
  которую snapshots должны использовать при space-aware cleanup. Минимальный
  объём свободного места контролирует отдельный параметр `FREE_LIMIT`.

`NUMBER_LIMIT="10"` не означает «10 пар снимков Portage». Такие пары создаёт
только отдельный hook, которого в указанном состоянии ASUS B5402 нет.

## Повседневное использование и восстановление

### Просмотр истории

```bash
snapper list
```

### Анализ изменений

```bash
# Посмотреть разницу в файлах между снимками 15 и 16
snapper status 15..16

# Посмотреть конкретные изменения в файле
snapper diff 15..16 /etc/conf.d/net
```

### Откат изменений

Перед откатом проверь выбранные номера снимков и список изменений. Команды
ниже изменяют текущие файлы.

```bash
# Откатить изменения между связанными снимками pre и post
snapper undochange 15..16

# Восстановить один случайно удалённый файл из снимка №10
snapper restore -s 10 /etc/fstab
```

## Verification и мониторинг

Проверь список снимков и состояние таймеров:

```bash
snapper list
systemctl status "snapper-*.timer"
systemctl list-timers "snapper-*"
```

Обычный `df` не показывает распределение данных Btrfs между субволюмами.
Размер каталога снимков можно проверить отдельно:

```bash
doas btrfs filesystem du -s /.snapshots
```

`snapperd` засыпает и запускается по требованию через D-Bus. Состояние
`static/inactive` само по себе не означает неисправность сервиса.

После настройки убедись, что:

- конфигурация `root` доступна ожидаемой группе;
- нужные timers активны и имеют следующее время запуска;
- новые снимки появляются в `snapper list`;
- cleanup соответствует заданным лимитам;
- использование места в `/.snapshots` остаётся ожидаемым.
