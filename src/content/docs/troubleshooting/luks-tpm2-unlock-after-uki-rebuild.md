Если при загрузке внезапно запрашивается пароль LUKS, хотя авторазблокировка
через TPM2 работала, сначала проверь журнал на mismatch TPM policy. На
эталонной системе ASUS B5402 перезачисление токена `systemd-tpm2` на PCR 7
восстановило авторазблокировку и было проверено реальной загрузкой.

Причина конкретного эпизода не доказана: смена cmdline совпала с проблемой,
но direct before/after measurement PCR 7 не выполнялся. Связь
`cmdline change → PCR 7 change → token invalidation` остаётся гипотезой.

## 1. Симптом

- При загрузке запрошен пароль LUKS вместо автоматической разблокировки.
- В журнале текущей загрузки:

```text
systemd-cryptsetup: TPM policy does not match current system state. \
Either system has been tampered with or policy out-of-date: Operation not permitted
```

## 2. Применимость и контекст инцидента

Решение проверено на эталонной системе ASUS B5402 со следующей boot chain:

- systemd-boot;
- UKI с Dracut-генератором;
- sbctl;
- токен `systemd-tpm2` на PCR 7.

Это конфигурация проверенной эталонной системы, а не универсальная TPM policy.
Другая firmware, другой PCR set или другая boot chain могут вести себя иначе.

## 3. Диагностика

### Шаг 1 — проверить журнал текущей загрузки

Подтверди класс ошибки:

```bash
journalctl -b -u systemd-cryptsetup@cryptroot.service --no-pager
```

### Шаг 2 — проверить историю в persistent journal

История `Starting` / `Finished` по всем загрузкам показывает, когда проблема
появилась и работала ли авторазблокировка раньше:

```bash
journalctl -u systemd-cryptsetup@cryptroot.service --no-pager -o short \
  | grep -E 'Starting Crypt|Finished Crypt|does not match'
```

В контексте этого инцидента тайминг служил индикатором:

- `Starting → Finished` за 1–2 секунды — авторазблокировка;
- 15–25 секунд и пара `does not match` — пароль вводили руками.

Это наблюдение на эталонной системе, а не универсальная гарантия для любой
конфигурации.

### Шаг 3 — посмотреть состав токена

Путь LUKS-раздела эталонной системы — `/dev/nvme1n1p2`. Свой раздел с
`crypto_LUKS` найди через `lsblk -f`:

```bash
doas cryptsetup luksDump /dev/nvme1n1p2 | grep -A20 '^Tokens:'
```

В блоке `Tokens:` ищи `tpm2-hash-pcrs` — это набор PCR токена.

> ⚠️ **Важный нюанс**: не трать время на эти пути (проверено 2026-09-14,
> systemd 261 / cryptsetup 2.x): у `systemd-cryptenroll` нет флага `--json`;
> в cryptsetup нет действия `token list`; **ID токена ≠ номер слота**
> (токены нумеруются отдельно и с нуля); тестовый
> `systemd-cryptsetup attach` корневого LUKS из работающей системы
> невозможен — устройство уже смонтировано («already in use»).
> Единственная честная проверка авторазблокировки — перезагрузка.

## 4. Что известно, а что остаётся гипотезой

### Подтверждённые наблюдения

- Авторазблокировка работала до эпизода 2026-09-14.
- После эпизода система запросила пароль, а journal содержал
  `TPM policy does not match current system state`.
- Перезачисление токена на PCR 7 восстановило авторазблокировку; результат
  проверен реальной загрузкой в тот же день.
- Пересборка ядра с тем же сертификатом подписи сама по себе unlock не
  ломала: переход 7.2.2 → 7.2.5 прошёл без последствий.

### Контекст PCR 7

Токен `systemd-tpm2` привязан к значению PCR — здесь PCR 7 банка sha256,
который в существующем описании связан с состоянием Secure Boot, ключами и
сертификатами. Изменение загрузочной цепочки, которое firmware измеряет в этот
PCR, делает токен недействительным. Среди таких изменений в документе
перечислены:

- перезапись ключей Secure Boot (`sbctl enroll-keys`) и обновления db/dbx;
- смена режима Secure Boot в BIOS.

### Correlation и гипотеза

Первая с момента настройки смена cmdline 2026-09-14 совпала с поломкой
авторазблокировки. Прямой before/after-замер PCR 7 тогда не выполнялся,
поэтому не установлено, измеряет ли firmware cmdline в PCR 7 напрямую. По
канонической модели cmdline относится к PCR 8/12.

Таким образом, подтверждённый факт — восстановление unlock после
перезачисления. Совпадение со сменой cmdline — correlation. Причинная цепочка
`cmdline change → PCR 7 change → token invalidation` не доказана и остаётся
гипотезой.

## 5. Исправление

Прежде чем применять:

- нужен живой слот с паролем, не TPM2: это recovery path; если пароль забыт,
  доступа к диску не будет;
- recovery-носитель не обязателен, но не помешает.

Перезачисли токен на текущее состояние PCR. Набор PCR подставь свой из шага 3;
команда спросит текущий пароль LUKS:

```bash
doas systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 \
  --wipe-slot=tpm2 /dev/nvme1n1p2
```

> **Важно**: `--wipe-slot=tpm2` удаляет **все** TPM2-слоты. Операция меняет
> LUKS2-заголовок; пароль слота 0 остаётся рабочим способом открыть диск
> при любом исходе.

## 6. Проверка

Единственная честная проверка авторазблокировки в этом сценарии — реальная
перезагрузка. После неё:

- пароль не запрошен;
- в журнале `Starting → Finished` за 1–2 секунды;
- сообщение `does not match` отсутствует.

## 7. Recovery после перезачисления

Обычный rollback состояния токена невозможен: предыдущий токен удалён wipe'ом
и не восстанавливается; к тому же он уже был нерабочим. Если новый токен не
сработал, диск открывается паролем слота 0, после чего enrollment можно
выполнить снова той же командой.

## 8. Как проверить correlation с изменением PCR

Сними значение PCR до и после подозрительного изменения — смены cmdline,
пересборки UKI или обновления sbctl — и сравни результаты:

```bash
doas tpm2_pcrread sha256:7 > ~/pcr7-before.txt
# ... изменение загрузочной цепочки и перезагрузка ...
doas tpm2_pcrread sha256:7 > ~/pcr7-after.txt
diff ~/pcr7-before.txt ~/pcr7-after.txt
```

Сравнение показывает, изменилось ли значение PCR 7 между двумя загрузками.
Для эпизода 2026-09-14 такого before/after measurement нет, поэтому его
причинность остаётся гипотезой.

### Отклонённая альтернатива на ASUS B5402

Радикальная альтернатива — PCR-подпись (`--tpm2-public-key` + ukify как
генератор UKI): авторазблокировка переживает любые пересборки ценой перехода
генератора UKI. На ASUS B5402 вариант отклонён 2026-09-14: инциденты редкие,
а восстановление требует одной команды. Это зафиксированное решение для
эталонной системы, а не общая рекомендация.

## 9. История наблюдений на ASUS B5402

- Март 2026 — 2 ошибки, апрель — 14. Эпизод прошёл сам, причину не искали.
- 2026-09-14 — первая смена cmdline с момента настройки: добавлен
  `audit_backlog_limit`. Она совпала с поломкой unlock.
- Перезачисление на PCR 7 восстановило авторазблокировку; результат проверен
  реальной загрузкой в тот же день.
- Before/after-замер PCR 7 не выполнялся. Причинная связь
  `cmdline → PCR 7` остаётся гипотезой до замера по разделу 8.

## 10. Incident/reference environment

Gentoo, systemd 261.2, cryptsetup 2.x, systemd-boot + UKI (генератор
Dracut), sbctl, firmware TPM; токен `systemd-tpm2`: PCR 7, sha256, SRK.
Проверено 2026-09-14. Это environment проверенного инцидента, а не утверждение
о current system state сегодня.
